# Site identity and signed usage reports

- Status: Draft, for the EmDash repo
- Date: 2026-11-28
- Discussion: [#4913 Track registry plugin usage](https://github.com/emdash-cms/emdash/discussions/4913)
- Related: [RFC 0001 Decentralized Plugin Registry](https://github.com/emdash-cms/emdash/blob/main/rfcs/0001-plugin-registry.md)
  (the planned site-identity follow-on, the reserved `auth` union),
  [#296 Marketplace Discussion](https://github.com/emdash-cms/emdash/discussions/296)
  (install-gated reviews), [#2041 Anonymous install counting](https://github.com/emdash-cms/emdash/discussions/2041)
- NSIDs below are proposals under `com.emdashcms.experimental.*`.

## Summary

Give each EmDash site an optional `did:web` identity: a key whose public half
the site serves in `/.well-known/did.json`. Use it first to sign the
plugin-usage reports #4913 asks for, so an aggregator can count sites that use
a plugin now, one per domain, without anyone being able to report for a site
they don't control. The same identity then serves install-gated reviews and
gated (paid) packages.

This replaces the hashed-secret scheme floated in #4913 with signatures. The
cost to an attacker is the same, one domain per counted site, but no secret
ever leaves the site, and any number of aggregators can verify reports
independently.

## Goals (from #4913)

- Count sites using a plugin **now**, not downloads or install events.
- Make inflation cost real resources per counted site, not one more request.
- Nobody can report for a site they don't control.
- Collect as little as possible per site; site owners can turn reporting off.
- No work added to pages served to visitors.
- Moderators can deal with a manipulated count.

Out of scope, as in #4913: native plugins installed from npm. They aren't
registry packages, and reporting them would leak private package names.

## Site identity

- **DID**: `did:web:{host}`, where `{host}` is the site's canonical public
  hostname. atproto supports only hostname-level `did:web` (no paths), so a
  site served under a path needs its own hostname to have an identity.
- **Document**: served by EmDash at `https://{host}/.well-known/did.json`,
  with one verification method holding the site key. Proposed fragment:
  `#atproto`, so the same key works anywhere atproto verifies JWTs (see Uses).
  See the open question on domains that already host someone's atproto DID.
- **Key**: P-256 (`ES256`), generated by EmDash when the identity is first
  enabled. WebCrypto supports it on every adapter, and it is a valid atproto
  key type. The private key lives in the platform's secret store where there
  is one (a Workers secret, an environment variable on Node), not in the
  database, so a database dump doesn't leak it.
- **Rotation**: replace the key and redeploy. Reports signed with the old key
  stop verifying once caches expire; the next daily report uses the new one.
- **Opt-in boundary**: having an identity does not mean reporting. Each use
  below is switched separately.

## Signed usage reports

**Transport.** Reports ride the existing daily update check: no work on the
request path. One procedure on the aggregator, proposed
`com.emdashcms.experimental.aggregator.reportUsage`.

**Authentication.** `Authorization: Bearer <jwt>`, the shape of atproto
service auth:

```json
{ "alg": "ES256", "typ": "JWT" }
{
  "iss": "did:web:example.com",
  "aud": "did:web:registry.emdashcms.com",
  "lxm": "com.emdashcms.experimental.aggregator.reportUsage",
  "iat": 1795161600,
  "exp": 1795161900,
  "jti": "<random>"
}
```

**Body.** Only registry packages, by their registry identity, and the version
installed:

```json
{
	"plugins": [{ "publisher": "did:plc:…", "slug": "seo", "version": "1.4.2" }]
}
```

No URL, locale, content, user counts or plugin settings.

**Verification by the aggregator.**

1. Resolve `iss`: fetch `https://{host}/.well-known/did.json` over https, no
   redirects, short timeout, cached by its own TTL. This fetch is the
   "call back to the site" from #4913: it proves control of the domain.
2. Check the signature against the document's key, `aud` is this aggregator,
   `lxm` is this method, `exp` is in the future and at most a few minutes
   after `iat`, and `jti` hasn't been seen in the replay window.
3. Replace the site's previous report. Nothing else is kept per site.

**Why signatures rather than a hashed secret.** With a secret sent on every
update, the aggregator (and anything that logs the request) holds a credential
that reports as the site, at every aggregator that trusts the same published
hash. A signature proves control without exposing anything, binds the report
to one aggregator through `aud`, and works with several independent
aggregators without coordination.

## Counting

- **Active**: a site counts for a package if its latest report, received in
  the last N days, lists it. Version distribution comes from the same reports.
- **Unit**: the headline count is distinct **registrable domains** (eTLD+1 by
  the Public Suffix List), not hosts. Subdomains are free: one wildcard DNS
  record and one Worker can serve unlimited `did:web:*.example.com` documents.
- **Free-hosting suffixes**: suffixes such as `workers.dev`, `pages.dev`,
  `netlify.app` and `vercel.app` are, to my knowledge, in the PSL's private
  section, which makes each subdomain its own registrable domain and brings
  free sybils back. Options:
  - use only the PSL's ICANN section, so each such platform collapses into
    one domain (resists sybils, undercounts real free-hosted sites);
  - count them, but report them as a separate figure;
  - count them with a per-suffix cap.

  Recommendation: report them separately, so the headline is the costly
  count and the honest total is still visible.

## Privacy

Domain-bound counting means the aggregator learns which domain runs which
plugin at which version. Published per site, that is a target list whenever a
vulnerability is disclosed. So:

- Reports are private calls to the aggregator. They are **not** atproto
  records, which would be public and signed.
- Only aggregates are published: per-package counts, and version
  distributions for publishers. Never site lists.
- Small counts are thresholded (for example, "fewer than 10"), for both
  totals and per-version figures.
- Only the latest report per site is stored, and it expires after N days. No
  IP addresses are stored.
- Site owners can turn reporting off (default on with notice, or opt-in, is
  an open question; #2041 proposed default on with opt-out).

## Moderation

- Reporting for a site you don't control is impossible without its key.
- Inflation costs a registrable domain per counted site; free-hosting
  suffixes are reported separately.
- Because reports are per site, moderators can see clusters that aggregates
  hide: many new domains reporting identical plugin sets, bursts of
  registrations, one suffix dominating a count. Actions: exclude domains or
  clusters from a count, or label a package's count as disputed through the
  existing labeller path.

## Other uses of the same identity

**Install-gated reviews (#296).** A review form appears only for a site with
a verified, current report for the package. Caveat: a review published as an
atproto record under the site DID discloses that the site runs the plugin,
which is the targeting risk above. Either reviews are authored by a person's
own atproto account with the aggregator only checking eligibility, or the
site accepts the disclosure knowingly. Open question.

**Gated (paid) packages (RFC 0001's reserved `auth`).** A proposed `auth`
variant, `com.emdashcms.experimental.package.release#spaceAuth`, names an
atproto space (permissioned data) holding the gated artifacts:

- The public release record stays signed in the publisher's repo with full
  metadata and the artifact `checksum`, with `requiresAuth: true` and no
  public blob. The aggregator indexes it like any other release.
- The bundle is a space blob, served only to readers holding a space
  credential, never by `sync.getBlob`. Cumulus stays out of gated bytes, as
  RFC 0001 requires.
- The space is managed by a licensing service (the publisher's, or a
  marketplace's) whose `checkAccess` answers from entitlements.
- To install, the site signs a delegation token with its site key, exchanges
  it for a credential, downloads the bundle, and verifies it against the
  **public** checksum before the normal consent flow. Licences are per site
  DID; revoking one stops downloads and updates, not running code.

This is why the key should be `#atproto`: atproto space hosts verify
delegation tokens against the issuer's `#atproto` key.

## Implementation sketch

- **Core**: key generation and storage; the `/.well-known/did.json` route; a
  signer for the report JWT; the report sent with the daily update check;
  settings for identity and reporting.
- **Aggregator**: DID resolution with caching; JWT verification and replay
  window; latest-report store with TTL; PSL-based counting; aggregates on the
  existing package APIs (e.g. `getPackage`), thresholded; moderation tools.
- **Directory**: show the count; whether it feeds sorting and ranking is a
  separate decision (#4913 notes that ranking is the strongest incentive to
  inflate).

## Phasing

1. Site identity and signed reports behind an experimental flag; aggregator
   counting; counts visible to publishers only.
2. Public counts with thresholds, once inflation and moderation have been
   observed in practice.
3. Reviews and gated packages as consumers of the identity.

## Open questions

- **A domain that already hosts an atproto `did:web`**: if someone's atproto
  identity is `did:web:example.com` and they run EmDash on `example.com`,
  there is one `did.json` and its `#atproto` key belongs to their PDS. Use a
  different fragment for the site key (works for reports, but not for space
  delegation tokens, which verify `#atproto`), require a separate hostname
  for the site identity, or let the site act through the person's DID for
  licences.
- Default on with notice, or opt-in.
- The active window N, and the thresholds.
- PSL policy for free-hosting suffixes.
- Whether a site may report to more than one aggregator.
- Reviews: site-authored (disclosing) or person-authored with eligibility
  checked by the aggregator.
- Key custody on adapters without a secret store.
